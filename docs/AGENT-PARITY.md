# LocModel 3.3.0 与 LocM Agent 能力对照

## 结论

LocM 和 LocModel 的 Agent **不能据现有证据认定为功能等同**。LocM 当前源码可确认：本地模型任务循环、工作区文件工具、系统原生危险操作确认，以及本次新增的受限工作区文本搜索。LocModel 3.3.0 安装包中则能静态找到 MCP、网页工具和电脑操作相关标识；由于没有成功打开其 Agent 页面，这些只是模块/资源线索，不证明它们已启用或可正常使用。

这次补上的高价值差距是工作区内只读文本定位，让 Agent 查项目符号、配置项或 TODO 时不必先把大量文件逐个读进上下文。它没有引入 shell 搜索、网络访问、MCP 或电脑控制。

## LocM：源码可确认

- Agent 通过已启动的本地模型进行 JSON 任务循环；新任务和追加要求先展示计划，再逐步调用工具。任务记录保存在本机 WebView 存储。
- 已接入列目录、读 UTF-8 文本、新建/修改文本文件、删除普通文件和运行程序。文件操作限定在用户选择的工作区，拒绝路径越界和符号链接，并避开 `.git` 元数据。
- **新增 `search_files`：** 按字面文本在工作区内搜索，可指定相对目录和大小写敏感选项。最多访问 500 个普通文件、最多 1,000 个目录项、递归深度 6、累计读取不超过 16 MiB；单文件超过 1 MiB 会跳过；最多返回 64 个匹配，每行片段最多约 240 字节。只处理 UTF-8 文本，跳过二进制内容、`.git`、符号链接和常见大型构建目录；触达上限时标记结果可能不完整。
- 覆盖、删除和命令在 UI 预览后仍由 Rust 后端实际弹出系统原生确认；取消不会执行，任务会暂停。**这套确认没有被本次改动弱化或绕过。**

**重要权限边界：** 命令仍以当前用户权限运行并继承环境变量，可访问工作区以外的文件和网络，也可能启动子进程。工作目录与系统确认都不是操作系统沙箱；直接进程的超时也不保证清理其后代进程。

LocM 目前没有实现 MCP、网页搜索/抓取、浏览器导航或电脑操作；也没有 OS 级进程沙箱。新增的文本检索是本地文件功能，不等于网页搜索或知识库。

## LocModel 3.3.0：仅有静态迹象

检查对象为用户提供的 `LocModel_3.3.0_amd64.deb`，SHA-256：`894dc1caf612d6de0bbb1f85ac9c6979b25ea9ce934344223c4e4f6a021d5a33`。包元信息标注 `loc-model` 3.3.0、amd64。静态文件清单包含主 ELF、图标和桌面入口，没有独立的 JS/HTML 文件；Agent 页面资源名称嵌在可执行文件中。

从 ELF 可读到 `agent.js`、`agentpage.js`、`mcp.js`，以及 `tool_read_file`、`tool_list_dir`、`tool_write_file`、`tool_run_command`、`tool_web_search`、`tool_web_fetch`、`agent_computer_action`、`computer_action`、`mcp_call` 等标识；也能看到 `src/tools.rs`、`src/mcp.rs`、`src/computer.rs` 等模块路径。这些支持“包内存在相关代码/资源名称”的判断，**不能证明**相应功能在 Agent 页面已启用、调用成功、权限如何控制或审批是否可靠。

## 实际未验证

LocModel 曾在禁网、隔离 HOME 的图形环境中尝试启动两次，均在窗口出现前以退出码 139 结束；本次没有重试。没有安装该包、登录、启动引擎、下载模型或触发文件操作，因此没有完成 LocModel 的页面交互级比较。

本次 LocM 改动通过默认目标 23 项测试和桌面目标 64 项测试，`cargo fmt --check` 与 Agent JavaScript 语法检查通过。新增搜索由 Rust 单测覆盖；未用真实模型运行 Agent，也未在桌面窗口中进行端到端操作。故不能声称 LocModel 的工具标识都可用，也不能声称两者完全功能一致。
